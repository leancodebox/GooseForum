# 访问控制性能基线

基准固定生成 100,000 个已发布主题和 100 个主分类，使用首页默认排序与 20 条分页，分别模拟 95%、50%、5% 分类可见率。受众条件直接作用在 `main_category_id`，不连接分类关系表；排序复合索引保持原列顺序。实测把主分类插入排序索引会让高可见率场景产生大范围分段扫描和额外排序，因此没有采用。

同一基准分别使用 SQLite 内存库和测试临时目录中的文件库。文件库会在测试结束后自动清理。

复现：

```bash
go test ./app/models/forum/topics -run '^$' \
  -bench '^BenchmarkAudienceTopicList100K(File)?$' \
  -benchtime=100x -count=5 -benchmem
```

2026-08-13，Apple M4，主分类标量过滤的 Go benchmark 结果。平均延迟是五轮 `ns/op` 的平均值；P95 是五轮各自 P95 的中位数：

| 存储 | 可见率 | 平均延迟 | P95 | 分配 |
| --- | ---: | ---: | ---: | ---: |
| 内存 | 95% | 0.276 ms | 0.295 ms | 51.3 KB / 1,412 allocs |
| 文件 | 95% | 0.283 ms | 0.318 ms | 51.8 KB / 1,416 allocs |
| 内存 | 50% | 0.275 ms | 0.287 ms | 46.1 KB / 1,321 allocs |
| 文件 | 50% | 0.286 ms | 0.299 ms | 46.6 KB / 1,325 allocs |
| 内存 | 5% | 0.450 ms | 0.466 ms | 40.6 KB / 1,227 allocs |
| 文件 | 5% | 0.468 ms | 0.482 ms | 41.2 KB / 1,231 allocs |

文件库的平均延迟比内存库高 2.4%～4.2%，P95 中位数高 3.3%～7.7%。文件库在写入种子数据后立即查询，数据库页通常仍在 SQLite 和操作系统缓存中，因此这是文件持久化路径的热缓存基线，不代表冷启动或物理磁盘随机读取延迟。

该基准不进入普通测试路径，避免每次 `go test ./...` 重建 10 万行数据。MySQL 的执行计划和 P95 应在实际部署版本、数据分布与连接参数下用同一查询补录；不能从 SQLite 数字外推。

## 分类页查询基线

分类页还要通过 `topic_category_index` 判断主题是否带有当前分类，再用 `topics.main_category_id` 判断当前用户能否读取主题。独立基准生成 100,000 个主题、100 个均匀分布的主分类，并为每个主题增加一个共同的辅助分类；前 10 个最旧主题再增加一个稀疏辅助分类。查询使用真实分类页的默认排序和 21 条读取（20 条结果加 `HasNext` 探测）。

复现最终分类页实现，每个场景执行 100 次并重复 3 轮：

```bash
go test ./app/models/forum/topics -run '^$' \
  -bench '^BenchmarkCategoryTopicList100K' \
  -benchtime=100x -count=3 -benchmem
```

初始相关 `EXISTS` 查询的结果如下，用于记录优化前基线：

| 存储 | 分类场景 | 平均延迟 | P95 |
| --- | --- | ---: | ---: |
| 内存 | 主分类占全站主题 1% | 1.488 ms | 1.559 ms |
| 文件 | 主分类占全站主题 1% | 1.612 ms | 1.629 ms |
| 内存 | 全站辅助分类，95% 主分类可见 | 0.335 ms | 0.375 ms |
| 文件 | 全站辅助分类，95% 主分类可见 | 0.344 ms | 0.392 ms |
| 内存 | 全站辅助分类，50% 主分类可见 | 0.335 ms | 0.398 ms |
| 文件 | 全站辅助分类，50% 主分类可见 | 0.342 ms | 0.360 ms |
| 内存 | 全站辅助分类，5% 主分类可见 | 0.603 ms | 0.646 ms |
| 文件 | 全站辅助分类，5% 主分类可见 | 0.663 ms | 0.833 ms |
| 内存 | 仅 10 个最旧主题的稀疏分类 | 111.644 ms | 112.061 ms |
| 文件 | 仅 10 个最旧主题的稀疏分类 | 121.458 ms | 121.908 ms |

初始实现的常规分类页为亚毫秒到约 1.6 ms。稀疏且主题很旧的分类暴露出明确的尾部成本：相关 `EXISTS` 查询按全站列表索引顺序扫描主题，再逐条查询分类索引；当不足 20 条结果且命中项位于排序尾部时，可能扫描接近全部主题。内存库同样复现约 112 ms，说明主要成本来自查询形态，而不是文件 I/O。

最终实现采用两种有上限的查询路径：

- 先使用 `(effective, category_id, topic_id)` 复合索引探测最多 257 个成员 ID。
- 成员数超过 256 时，使用分类索引 `JOIN topics`，继续由数据库完成受众过滤、排序和分页。
- 成员数不超过 256 时，只按主键批量读取这些主题；在最多 256 条记录内完成状态、作者、标题、`main_category_id` 受众过滤、排序和分页，避免 SQLite 为满足全站排序或大范围 `IN` 条件选错索引。

最终结果如下。平均延迟是三轮 `ns/op` 的平均值；P95 是三轮各自 P95 的中位数：

| 存储 | 分类场景 | 平均延迟 | P95 |
| --- | --- | ---: | ---: |
| 内存 | 主分类占全站主题 1% | 0.836 ms | 0.851 ms |
| 文件 | 主分类占全站主题 1% | 0.874 ms | 0.888 ms |
| 内存 | 全站辅助分类，95% 主分类可见 | 0.242 ms | 0.320 ms |
| 文件 | 全站辅助分类，95% 主分类可见 | 0.251 ms | 0.315 ms |
| 内存 | 全站辅助分类，50% 主分类可见 | 0.237 ms | 0.303 ms |
| 文件 | 全站辅助分类，50% 主分类可见 | 0.248 ms | 0.272 ms |
| 内存 | 全站辅助分类，5% 主分类可见 | 0.376 ms | 0.382 ms |
| 文件 | 全站辅助分类，5% 主分类可见 | 0.394 ms | 0.417 ms |
| 内存 | 仅 10 个最旧主题的稀疏分类 | 0.071 ms | 0.074 ms |
| 文件 | 仅 10 个最旧主题的稀疏分类 | 0.081 ms | 0.084 ms |

文件库稀疏尾部的 P95 从 121.908 ms 降至 0.084 ms；常规分类场景也没有以回退换取尾部改善。阈值使应用层排序的内存和 CPU 上限固定，较大分类仍交给数据库索引与排序处理。基准直接调用生产仓储的 `PageWithDB`，不另外复制查询实现。

与主列表基准相同，文件库结果是种子写入后的热缓存基线；测试只包含数据库查询和 GORM 实体装载，不包含 HTTP、Payload 转换、JSON 编码或前端渲染。

“受限分类只允许单选”作为独立的数据不变量实现：公开分类可多选；一旦选择受限分类，它必须是主题唯一分类。该规则降低权限语义复杂度，但分类页优化仍独立覆盖公开辅助分类和所有稀疏分类，不依赖受限分类单选来获得性能。
