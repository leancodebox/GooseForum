# 热门排序

热门列表只读取 `topics.rank_score DESC, id DESC`。首页和分类页规则一致，其他排序不变。分数为 `int64`，1 分存为 1000。

## 数据职责

`topics` 保存内容、冗余互动计数、首次发布时间 `published_at` 和分数 `rank_score`。首次发布时间在发布保存流程中初始化，已有时间不会被普通保存或重算重置；评分更新不改变 `updated_at`。

`topic_rank_schedule` 独立保存调度状态：

- `topic_id`：主键，一个主题最多一条调度记录。
- `next_run_at`：下次执行时间，有索引；为空表示当前无需处理。
- `version`：触发和任务确认时递增，防止旧任务覆盖新触发。

沉降时保留调度行和版本，不删除再插入，因此版本不会重置。`topics.next_rank_at` 及 `idx_topics_rank_due` 已从模型移除，由升级迁移删除数据库中的旧字段和索引。

## 计分只读取一条主题记录

Worker 从队列取到任务版本后，按主题主键读取已保存的 `like_count`、`reply_count`、`published_at`、`created_at`、`last_posted_at`、状态和删除标记。计分不读取调度表以外的辅助表，不查询回复或行为明细，不使用 SUM、COUNT、GROUP BY，也不重新校准互动统计。

一次正常重算包含一次主题读取、一次主题分数更新和一次调度确认，另有摊薄到每批的队首查询。与旧合表实现相比，每个主题增加一次调度写入；不会增加列表 JOIN。显式重算命令还需要读取任务版本，缺失任务时会初始化调度行，这些准备步骤不进入 Worker 的日常处理路径。

## 当前公式

对数压缩 `G(x, cap) = ln(1 + min(x, cap)) / ln(1 + cap)`，通过百万分之一精度的整数查表近似实现，运行时只使用整数运算。

- 点赞：`6 × G(like_count, 50)`，最多 6 分。
- 回复：`14 × G(reply_count, 100)`，最多 14 分。
- 新鲜度：发布后 0～6 小时 30 分，6～12 小时 24 分，12～24 小时 18 分，1～2 天 12 分，2～3 天 8 分，3～7 天 4 分，之后 0 分。
- 最近回复活跃度：距最后回复不满 1 小时 20 分，1～6 小时 12 分，6～12 小时 6 分，12～24 小时 2 分，之后 0 分。只有 `reply_count > 0` 且最后回复时间存在才计入。

历史底分最高 20，活跃加分最高 20，新鲜度最高 30，总分最高 70（存储值 70000）。新鲜度和活跃度按分档边界安排下次重算；都归零后保留历史底分，调度时间置空。草稿、屏蔽或删除主题计零分并停止调度。

为避免临时聚合，当前不计算独立评论人数、每人回复上限、近 24 小时精确互动量，也不排除作者自赞或自己的回复。屏蔽回复参与计分，沿用原有冗余计数；删除后的数量和最后回复时间依赖业务维护。阅读数不计分。

## 触发、确认与失败

业务完成后通过现有事件总线的 `topicrank.Notify` 发送主题 ID 和发生时间。点赞通知在原有 `IncrementLike` / `DecrementLike` 原子 SQL 成功后发送；主题与回复创建仍在原有业务事务提交后通知。Notify 不访问数据库。

处理器使用一次 UPSERT 创建或更新调度行，保留最早到期时间并递增版本。它只写调度表，不修改主题发布时间或计数。成功后发送一个可合并的本地唤醒信号。

Worker 写入分数成功后，以 `topic_id` 和读取的 `version` 条件更新下次时间并递增版本。如果期间收到新触发，旧版本确认不影响新调度；后续消费会重新读取最新主题数据。主题已被物理删除时，也按版本把任务置为无待处理状态，避免反复重试不存在的主题。

主题写入失败时，在独立调度表上按版本延后 30 秒重试，让其他任务继续消费。独立表可以隔离主题行本身的更新失败，但不能隔离数据库整体故障或 SQLite 全库写锁。队列读取或重试写入失败时退避 1 秒。

评分不主动调用 Transaction/Begin，也不单独设置 SkipDefaultTransaction，沿用项目的 GORM 默认行为。源数据保存和任务入队仍不是一个跨表原子操作；内存事件总线仍采用尽力投递。进程在业务保存与入队之间退出可能漏触发，拆表不提供 exactly-once 保证。分数写入成功、任务确认前退出可能导致下次重复计算，但不会触发明细聚合。

## 平滑消费与配置

排序不再注册 cron，服务启动后使用单个常驻 Worker。每批最多读取队首 20 个任务，逐条到期处理。默认上限 20 条/秒，每条处理完成后至少等待 50ms；额度不累积，慢查询后不集中补发，跨批次也不能绕过间隔。

未来任务按到期时间等待，空闲等待最长 5 秒，兜底其他进程发来的标记。本地唤醒只能结束空闲等待，不能跳过限速或故障退避。每个数据库操作有 5 秒超时，停机取消等待和数据库操作；待处理状态留在表内供重启继续消费。

```toml
[ranking]
worker_enabled = true
max_per_second = 20
```

配置启动时读取。`max_per_second` 接受 1～1000，未配置或无效时使用 20。多实例共库时只允许一个实例开启 Worker，其余实例设为 false；当前没有分布式租约，多消费者不能仅靠版本确认保证分数写入顺序。执行手动重建时也应避免和 Worker 并行消费同一批任务。

有处理活动时每 30 秒记录处理数、失败数及观察到的到期延迟，不为日志进行队列 COUNT。持续到达速率超过预算或数据库能力时仍会积压，需要结合负载调整处理预算，不能无限速重算。列表缓存仍可能额外延迟最多约 5 秒。备份等其他任务继续使用 cron。

## 升级与手动刷新

迁移版本 23 先创建独立调度表，再按主题 ID 每批 200 条复制旧字段中的非空待处理时间。已有调度行保持原样，支持中断后重跑；不读取互动明细、不统计互动、不重算分数。全部复制成功后才删除旧索引和 `topics.next_rank_at`。无旧字段的新库直接使用新表。

升级时需停止仍使用旧字段的应用实例，再启动新版完成迁移。删除字段属于一次性 DDL，SQLite 会改写表数据；使用原生 DROP COLUMN 保留其他索引，不使用会丢失二级索引的 ORM 重建路径。关闭自动迁移时，必须先完成对应表结构和数据迁移。

```bash
go run . rebuild-topic-ranks
# 或使用重新构建的二进制：
./gooseforum rebuild-topic-ranks
```

命令支持取消，按 ID 分批处理开始时已有的主题，保留首次发布时间，不重建互动统计。公式集中在 `app/service/topicrankservice/score.go`。原版本 22 的首次历史评分回填继续保留；从已经完成版本 22 的数据库升级到版本 23，仅搬运调度数据。

## 封装与测试

`topicrank.go`、`topicrank_connect.go`、`topicrank_rep.go` 分离模型、默认连接入口和调度操作，不传递 `*gorm.DB`；`context.Context` 用于超时和取消。分数、发布时间和主题 ID 查询归 `topics` repository。

测试覆盖平滑限速、跨批次消费、SQL 数量及无聚合、重试和取消、处理中收到新触发、沉降后版本不重置、主题写入失败不阻塞其他主题，以及迁移跨批次中断续跑、旧字段/索引删除、其他索引和主题数据保留。计分测试只创建主题表和调度表，不依赖互动明细表。
