# 热门排序

热门列表只读取 `topics.rank_score DESC, id DESC`。首页和分类页规则一致，其他排序不变。分数为 `int64`，1 分存为 1000；无作者等级、无新增评分事务、无版本字段。

## 计分只读取一条主题记录

`Recalculate` 按主题 ID 读取以下已保存字段，再做固定次数的整数运算并写回分数和下次时间：

- `like_count`：累计点赞数。
- `reply_count`：累计回复数。
- `published_at`：首次发布时间，历史数据缺失时用 `created_at`。
- `last_posted_at`：最后回复时间。
- 状态和删除标记：决定主题是否可计分。

不查询回复表、用户行为表或用户统计表；没有 `SUM`、`COUNT`、`GROUP BY`、去重或读取明细后循环求和。单次重算成本不随回复数或参与人数增长。重算命令获取最大 ID 也使用索引倒序取一条，不做聚合。

## 当前公式

对数压缩 `G(x, cap) = ln(1 + min(x, cap)) / ln(1 + cap)`，通过百万分之一精度的整数查表近似实现，运行时只使用整数运算。

- 点赞：`6 × G(like_count, 50)`，最多 6 分。
- 回复：`14 × G(reply_count, 100)`，最多 14 分。
- 新鲜度：发布后 0～6 小时 30 分，6～12 小时 24 分，12～24 小时 18 分，1～2 天 12 分，2～3 天 8 分，3～7 天 4 分，之后 0 分。
- 最近回复活跃度：距最后回复不满 1 小时 20 分，1～6 小时 12 分，6～12 小时 6 分，12～24 小时 2 分，之后 0 分。只有 `reply_count > 0` 且最后回复时间存在才计入。

历史底分最高 20，活跃加分最高 20，新鲜度最高 30，总分最高 70（存储值 70000）。新鲜度与活跃度只在分档边界重算。

为避免临时聚合，当前不计算独立评论人数、每人回复上限、近 24 小时精确互动量，也不检查作者自赞和自己的回复。屏蔽回复参与计分，沿用已有冗余计数；删除后的数量和最后回复时间依赖现有业务维护。接受冗余计数暂时不准确，不在重算时校验或修复统计。阅读数仍不计分。

## 更新和调度

业务保存后通过 `topicrank.Notify(topicID)` 发布现有事件总线的 `TopicRankRequested` 事件，不使用 `AfterSave` 评分钩子。Notify 不访问数据库，也不等待处理器写入；主题与回复创建在已有业务事务提交后发布。处理器异步写入重算标记，错误交给总线按既有策略重试；事件只携带主题 ID 和发生时间，不携带请求上下文或事务连接。首次发布时间采用事件发生时间，避免消费延迟影响新鲜度。评分通过 `topicrank.State` 的 GORM `Model` / `UpdateColumns` 写入，不更新主题的 `updated_at`。普通主题对象的派生字段保持只读，避免旧对象覆盖分数。

复用现有 cron，每 30 秒最多处理 200 个到期主题，单轮超时 20 秒，单进程不重叠。`next_rank_at` 有索引，只读取到期 ID，不周期扫描全站。普通重算每个主题一次主键读取和一次更新；正常负载下更新约需 30 秒，加列表缓存最多约 5 秒，积压时延迟会增加。

新鲜度与活跃度都归零后，`next_rank_at = NULL`，保留历史底分并停止调度。新互动可重新激活。草稿、屏蔽或删除的主题到期后清零并停止调度。

评分不额外开事务，事件最终失败会由总线记录日志。事件总线是现有内存队列，沿用其尽力投递语义。并发写入可能暂时留下旧分数，后续互动、已有调度或手动重算可修正。原有业务事务不变。

## 手动刷新

```bash
go run . rebuild-topic-ranks
```

重新构建的二进制也可执行 `./gooseforum rebuild-topic-ranks`。

命令先按配置运行迁移，再按 ID 每批 200 个主题重算，包含沉降主题，并打印累计处理数量。可以重复运行，不重置首次发布时间，不重建互动统计。只处理开始时已有的主题；期间新主题走正常调度。自动迁移关闭时需先更新表结构。

迁移版本 22 的首次回填按原创建时间初始化已有公开主题的首次发布时间。后续手动重算保留首次发布时间。公式集中在 `app/service/topicrankservice/score.go`；调整公式后用上述命令刷新全部分数。

测试只创建主题表即可运行完整计分、调度和全量重算，以保证评分不依赖其他表；另覆盖时间分档、沉降、整数上限、首次发布、旧对象保存和列表排序。
