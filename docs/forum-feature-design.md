# GooseForum 功能规划与安全设计

日期：2026-10-03。状态：本轮六项功能已实施，本文保留设计依据与后续预案。
基线：本地 main `eca0cd97`；未修改现有运行配置。

本轮交付：Markdown 扩展与用户提及、双因素认证、本地草稿恢复、账号限制、
登录安全记录、注册限制。投票、邀请审批、Passkey 等后续预案尚未实现。
具体运行规则以 [Markdown 扩展](markdown-extension-design.md)、
[双因素认证](two-factor-authentication.md)、[账号限制](account-restrictions.md)、
[登录安全记录](login-security-history.md)、[注册限制](registration-controls.md) 为准。

本轮验证：全量 Go 测试、八个安全相关包 race、前端 238 项单元测试、类型检查、
lint、模块边界、国际化、死代码扫描与生产构建通过；浏览器桌面/手机测试 68 项通过、
2 项按视口跳过。独立 CR 发现的角色权限绕过、回复竞态、邮箱恢复和未知扩展解析
问题已修复并复核。SQLite 已验证；MySQL/PostgreSQL 和真实 SMTP 投递未实测。

已知检查例外：包体积预算未通过。隔离构建基线 HEAD 的站点壳/中文首页分别为
207.8/229.7 KiB gzip（预算 198/215），本轮为 211.4/234.3；未调整预算。
MFA 只从私有 `app.signingKey` 派生专用密钥；挑战、身份写锁和限流的第一版运行边界为单实例。

目标：可靠、好用，保持单机运行成本和代码可维护性。明确业务数据一致性需要时
才使用事务，不引入用于断电恢复的持久化任务、队列或后台重试框架。
浏览器本地草稿保存是本轮明确提出的用户功能，不扩展为后端任务恢复体系。

## 3. 双因素认证

### 3.1 范围与用户流程

第一版采用标准 TOTP 验证器 + 一次性恢复码。采用稳定 Go 库实现算法，
不自行实现密码算法，不同时增加短信验证码、Passkey 或信任设备绕过。

```text
设置：近期身份复验 -> 生成待确认密钥 -> 扫码 -> 输入验证码
    -> 原子启用 -> 展示恢复码 -> 撤销全部登录会话

登录：验证密码/第三方身份 -> 检查账号政策 -> 创建短期挑战
    -> 验证 TOTP/恢复码 -> 再检查政策 -> 签发普通会话
```

- 只有启用后才生效，扫码而未确认不能锁住用户；待确认状态 10 分钟过期。
- TOTP 建议 6 位、30 秒，允许相邻一个时间步漂移；服务器时间必须准确。
- 恢复码建议 10 个，每个至少 128 位随机性，使用可输入/复制的分组编码，
  仅展示一次，数据库仅保存 hash，不记录到日志。
- 使用恢复码登录后提示剩余数量；重新生成需近期完整身份复验，旧码整体失效。
- 关闭/更换 TOTP 需要近期第一因素 + 当前 TOTP 或恢复码，
  完成后撤销全部会话、待用挑战并记录安全事件。
- 忘记密码不关闭 MFA。丢失全部第二因素时，进入有记录的管理员恢复流程，
  邮箱链接不能单独绕过 MFA；管理员恢复不得读取旧密钥。
- 未启用用户流程不变。管理员强制启用策略后置，但页面和契约可预留 enforcement 状态。

### 3.2 登录入口统一

- 密码登录、OAuth/OIDC 回调创建站内会话，都必须经过统一“完成认证”服务。
  第一版对已启用 MFA 的账号总是验证本地第二因素，不凭上游声称的 MFA 直接跳过。
- MFA 完成前不设置 access_token，不返回可访问普通 API 的登录凭据。
- 挑战使用独立、随机、不透明标识，5 分钟有效，绑定用户、第一因素结果、
  认证方法、token/security version 及经过校验的站内跳转目标。
  不把密码、TOTP secret 或 OAuth access token 放进浏览器挑战载荷。
- 挑战存在受限容量的进程内专用 TTL 存储中，原子消费；重启后重新登录。
  不使用通用 sharedcache，不假定其能提供一次性消费。第一版范围为单实例。
- 失败限流同时按账号/IP/挑战实施，建议每挑战最多 5 次；重新申请挑战不能清零账号限制。
- MFA 设置和改密码要求本次操作提供本地密码，已开启 MFA 时同时提供第二因素；
  改邮箱、解绑 OAuth 要求已开启的第二因素。没有独立的五分钟复验票据。
  OAuth 专用账号需通过已验证邮箱设置本地密码后绑定 MFA，上游强制重新认证后置。
- 论坛作为 OIDC Provider 时，已有有效会话可按正常有效期工作；客户端要求重新认证时
  必须走完整流程，MFA 前不能签发授权码。已发行的外部令牌不因站内退出自动撤销，
  其封禁/撤销检查和有效期需要在身份模块单独覆盖。

### 3.3 数据与一致性

- `UserMFA` 记录 user ID、密钥密文、启用时间、最后接受的 TOTP 时间步。
  第一版使用 HKDF-SHA256 从私有 `app.signingKey` 派生专用密钥和 AES-GCM，
  不引入额外密钥配置，密钥轮换后置，
  不能使用公开配置或数据库内同存的密钥。
  配置缺失时不得开启新绑定；已有绑定无法解密时不得静默跳过验证。
- 恢复码单独存 hash、使用时间，唯一约束避免重复；校验/消费必须并发安全。
- 持久化最后使用时间步是防重放所需的安全数据，不是断电任务恢复机制。
  更新使用“仅接受更大时间步”的条件，合法漂移窗口内已用码也不能再次接受。
- 验证成功后，TOTP 时间步/恢复码消费和会话记录创建在必要的小事务内完成；
  成功提交后才发 cookie。并发请求不能消费同一码得到多个会话。
- MFA 启用、关闭及管理员恢复引起安全版本更新，旧挑战和其他会话失效；
  与密码变更已有 TokenVersion 机制统一设计，避免产生两套失效规则。
- CSRF、挑战绑定与客户端校验沿用现有应用安全边界，敏感接口补齐验证。

验收：RFC 测试向量、时间漂移、重放、并发消费、OAuth 绕过、旧会话复验、
密钥缺失、恢复码耗尽、改密/封禁后挑战无效。RFC 6238 和 NIST 的 OTP 重放/限流要求
作为技术参考，本文不宣称达到特定认证等级。

## 4. 增强本地草稿恢复

### 4.1 目标与范围

降低刷新、误关闭和网络失败造成的输入丢失。保留已有服务端主题草稿和离开保护，
增加浏览器本地副本；不宣称跨设备同步，也不宣称浏览器关闭前最后一次输入一定写入。

第一版覆盖新主题、主题编辑、新回复、回复编辑；私信、简介和公告后续单独评估。
底层保存 Markdown 原文和业务输入，避免保存 ProseMirror 私有对象或生成 HTML。

### 4.2 存储与生命周期

- 采用浏览器 IndexedDB，通过成熟薄封装操作；不使用 Service Worker 或后台同步队列。
- 主键包含版本、站点、user ID、编辑类型、对象 ID 和本次编辑实例 ID。
  每个账号、编辑类型与对象只保留最新一份草稿；实例 ID 用于版本与提交清理，
  不作为展示历史副本的依据。新主题使用对象 ID 0，其本地草稿同样只保留一份。
- 字段包含标题、原始正文、板块 ID 的有序数组、回复目标、源文版本、
  原服务端修订/更新时间、更新时间和本地 revision；不保存密码、会话 token 或 MFA 信息。
- 编辑稳定后 1 秒防抖保存，有变化时最多每 5 秒保存一次；串行处理本实例写入，
  revision 防止旧快照覆盖新快照。失焦/pagehide 尽力保存，不依赖 unload。
- 自动保存发生在组件卸载前的状态所有者层，切换编辑模式、最小化不能创建第二份草稿。
- 保存 14 天，每个编辑对象保留一份，每账号最多 50 个对象、总正文大小 10 MiB。
  标题和正文均为空白时不保存，清空输入仅删除当前实例的草稿；
  打开编辑器/草稿页时清理历史空白、过期和同一编辑对象的重复草稿。
  字节容量不足时保留已有副本并提示用户处理，不因保存失败额外删除内容。
- 无痕、存储拒绝或容量不足时保持编辑与发布可用，显示本地保存失败状态，
  不显示“已保存”；允许重试或复制内容，不用重复通知打断输入。
- 本地副本只保存已完成上传的引用；blob URL、未完成文件对象不能假装已恢复。

### 4.3 恢复、冲突与清理

- 先加载当前服务端内容与权限，再提示有本地草稿，默认不覆盖。
  提供恢复或不用两个选择；读取及选择未决期间暂停自动保存，避免覆盖旧草稿。
  选择不用会按版本清理该对象的本地草稿，恢复后继续自动保存。
- 服务端修订变化、板块权限变化或回复目标消失时显示差异/原因，不自动合并正文。
  无权读取的受限内容不在恢复列表展示摘要，也不能绕过当前写权限发布。
- 多标签页编辑同一对象共享一份最新草稿，通过存储事件提示新的本地草稿，
  暂停自动覆盖直到用户选择，不实现协同编辑或历史副本列表。
- 明确保存服务端草稿或发布成功后，仅删除本次提交 revision 对应的本地副本；
  提交期间产生的新编辑必须保留。规范化返回的 Markdown 更新保存基线。
- 审核待通过但已成功保存属于成功提交；审核拒绝或网络状态不明保留副本，
  不能自动重新提交产生重复主题。再次发送前由用户确认当前服务端状态。
- 退出、切换账号、发现会话失效时终止该账号的待写入操作，清理其本地副本，
  不把旧草稿写到下一账号。退出前存在未保存输入时提供现有离开确认。
- IndexedDB 不是保密存储；公共设备风险通过退出清理降低，不能宣称本地加密等于隔离。

验收：刷新、断网、恢复选择、跨账号隔离、同主题多标签页、异步写入顺序、
提交后继续编辑、规范化正文、存储失败、过期清理与附件失效。

## 5. 完善账号封禁

### 5.1 区分禁言和封禁

| 状态 | 登录/读取 | 发帖、回复、私信、上传、投票 | 账号安全操作 |
|---|---|---|---|
| 正常 | 按正常权限 | 按正常权限 | 允许 |
| 禁言 suspended | 允许 | 禁止 | 允许改密、MFA、撤销会话 |
| 封禁 banned | 不建立/不接受登录会话；仅访客可见内容 | 禁止 | 管理员处理，提供站外申诉信息 |

- 每种限制支持永久或截止时间，记录公开原因，必填操作原因。用户编辑框不显示管理员备注，既有备注保留在数据中。
- 现有 IsFrozen 主要阻止写入。旧冻结账号迁移为永久禁言以保留原有语义，
  不在无提示情况下升级为禁止登录；管理员可明确调整为封禁。
- 一个用户仅有一份有效限制记录，状态字段为唯一权威来源；过渡期间 IsFrozen 只作投影，
  禁止两个入口分别修改不同字段。最终移除兼容写入入口。
- 截止时间在权限判断时计算，不启动到期恢复任务；到期视为正常，但旧封禁会话不复活。
  限制记录保留到管理员明确修改，历史由操作记录呈现。

### 5.2 一致性与权限覆盖

- 设置封禁时更新状态并增加 TokenVersion，必要事务保证原子性，
  然后失效用户/会话/权限缓存。数据库有效状态是授权依据，不把删缓存当撤销本身。
- 设置禁言不撤销用于阅读和账号安全的会话，但立即阻止受限制的业务写入。
- 所有认证完成入口以及权限敏感写操作重新读取最小账号状态；
  封禁不能被旧会话缓存或 OAuth 回调绕过。
- 身份/角色/板块权限与账号限制共同生效，不能只在前端隐藏按钮。
- 与封禁请求同时在途的写入要定义顺序：在封禁提交后开始授权检查的操作必须拒绝；
  已完成检查的在途操作不承诺强制中断。要求更强语义的入口需独立并发控制。
- 管理后台、API、CLI 统一调用限制服务。禁言/封禁原因显示、分页历史和解禁复用现有后台风格。
- 普通管理员不能限制更高权限人员；禁止封禁自己或最后一个可管理站点的账号，
  并发修改管理员状态的保护须在数据库内保证业务一致性。
- 封禁不删除内容、不自动撤销外部应用已持有的所有令牌；
  OIDC 授权/刷新与已发行令牌的失效边界需一起验收。

验收：缓存已预热、旧 token、OAuth/MFA 挑战、临时限制到期、修改限制失败、
读写边界、最后管理员并发保护、外部认证入口。

## 6. 完善登录日志

当前 `user_auth_token_logs` 已记录 generate/logout/revoke 等动作、IP、UA，
保留期 90 天。登录失败目前主要在 slog，不能直接称为完整的可查询登录审计。

- 扩展现有日志体系，区分认证事件与会话事件，避免每次续期/活跃更新都算一次登录。
- 事件包括 login_success/login_failure、challenge_failure、MFA 启停/恢复、
  密码变更、会话撤销、账号限制变更；最终登录成功只有在普通会话创建成功后记录。
- 字段包含时间、已验证关联的 user ID（未知为 null）、认证方法/provider、
  结果及内部原因码、IP、截断 UA、可选 session ID/request ID。
- 未验证的登录名称不作为账号关联依据；可用带应用密钥的摘要辅助账号限流，
  不保存原始密码、密文登录载荷、TOTP、恢复码、cookie、OAuth token 或客户端 secret。
- 用户只能查看自己的已确认关联事件；未知或凭第一因素尚未证实的失败由管理员查看，
  防止把攻击者输入直接投影为某账号的真实行为。
- 页面提供时间/结果/认证方式筛选，分页与索引，不加载全量日志；
  用户侧摘要与管理员侧详细原因分开，外部登录错误保持一致，不泄露账号存在与否。
- 扩展现有 90 天清理，批量删除；攻击流量先限流，重复拒绝按窗口聚合或采样，
  成功登录和关键安全操作不采样，不为高频请求逐条写日志。
- 同请求审计记录不另外启动持久化任务。普通日志失败记录运行错误，
  不回滚已成功登录；关键安全操作历史与状态在确需一致时同事务保存。
- IP 只信任配置的反向代理来源，不按任意 X-Forwarded-For 取值；
  不默认接外部 IP 地理定位服务，不增加每次登录的外部请求。

验收：成功/失败事件、无账号泄露、代理 IP、日志写入失败、保留清理、
管理员/本人查询权限、异常请求的写入量上限。

## 7. 完善注册限制

### 7.1 第一版

- 复用并扩展 `SecurityAndRegistration`，注册政策由同一个服务判断。
  密码注册、OAuth 首次创建账号、未来其他自助创建入口必须执行它。
- 注册关闭不影响已有账号密码/OAuth 登录及绑定；
  OAuth 回调先判定已有绑定，只有创建新账号时应用注册政策。
- 邮箱验证、允许域名、验证码继续保留。域名先规范化为小写 ASCII/IDNA，
  默认精确匹配，不用字符串后缀误放行；子域策略只有明确配置才允许。
- 要求邮箱时，上游未给邮箱或未验证邮箱必须补齐本地验证，
  不把同邮箱的第三方账号自动绑定到已有账号。
- 按可信 IP、邮箱目标和全站总量设置有界限流；计数器有 TTL、容量和明确错误返回。
  登录、验证码发送、密码重置各自限额，不能通过反复发邮件绕过注册限制。
- 同邮箱重复创建与同用户名竞争依赖数据库唯一约束；实施前核对并处理历史重复，
  明确 SQLite/MySQL/PostgreSQL 的规范化和大小写规则。
- 账号创建、初始角色和首个管理员规则一致，首个管理员的并发保护不得靠“先查数量再插入”。
- 不使用长期自动账号锁定处理恶意尝试，避免攻击者通过失败请求封住受害者。
  限流可使用进程内专用存储；重启重置是明确边界，第一版不宣称跨实例一致。

### 7.2 后续注册模式预案

| 模式 | 行为 |
|---|---|
| open | 通过基本政策后创建账号 |
| closed | 禁止自助创建，保留已有账号登录 |
| invite | 必须有有效邀请，其他政策仍执行 |
| approval | 创建待批准账号，只能进入账号状态/验证界面 |

第一版先完成 open/closed 和统一限制，不顺带实施邀请/审批。
后续 mode 替代 EnableSignup 时需要配置迁移，不能同时保留两个冲突开关。
邀请以随机 token 的 hash 存储，限制次数/有效期，可选绑定邮箱；
消费与创建账号必须原子完成。注册审批不复用“邮箱未验证”字段，二者状态独立。
管理员创建和 CLI 创建必须有明确的管理权限和审计，不隐式接受用户请求的绕过参数。

验收：关闭注册后旧 OAuth 登录、OAuth 首次创建、缺邮箱、域名及子域、
IP 限流、邮件轰炸、并发唯一性、首个管理员、未来邀请与审批状态。

## 8. 模块边界与实施顺序

认证政策、账号限制和审计由后端统一服务负责；前端只装配流程和反馈，
错误继续使用项目现有消息码与国际化。小读模型按 `Model(&完整模型{}).Find(&读模型)`
加载，避免在每个调用方复制 Select 字段列表。

| 阶段 | 产出与验收入口 |
|---|---|
| 设计确认 | 语法家族、稳定提及、旧内容版本、禁言/封禁语义及草稿退出清理 |
| 账号安全基础 | 注册政策与账号限制统一、登录审计增强；独立于 Markdown |
| Markdown 功能 | 扩展 fixtures/编辑往返，再接 @提及的身份、候选与通知 |
| 其他独立功能 | TOTP、本地草稿分别实施并验收，不依赖 Markdown 扩展框架 |
| 后续语法验证 | details/note/spoiler、投票，验证块级解析和业务一致性 |
| 后续需求 | 关注流、搜索等按实际优先级单独设计 |

任何新增模型先通过现有迁移体系落库；改动 resource 后按 config.toml 的环境执行 dev/build。
验证按风险选择解析用例、权限/API 回归、三种数据库一致性、前端状态和桌面/手机交互；
不因为功能名相同就认定三个数据库并发行为一致。

## 9. 待讨论的产品选择

以下已有建议默认值，尚未认定为最终决定：

1. 自定义标签家族采用 `[name ...]...[/name]`；@输入保存成稳定 ID 标签。
   代价是源码模式看到更长语法，收益是改名和复制时身份明确。
2. 旧冻结状态保留禁言语义，新封禁明确禁止登录；二者分别管理。
3. 本地草稿默认 14 天，退出/切换账号清理，偏向公共设备隐私。
4. TOTP 对已启用账号的密码和第三方登录都执行；不在第一版提供信任设备绕过。
5. 先做注册入口统一和限流；邀请/人工审批作为独立后续功能。
6. 投票作为语法预案；是否排在其他社区功能之前待确定。

这些选择可以在实现前调整；没有为了等确认而停止设计，也没有提前修改线上行为。
