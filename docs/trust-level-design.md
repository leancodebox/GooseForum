# 信任等级设计与实现

状态：已实现并完成本地验证（2026-10-16）。不提供等级系统总开关，不提供等级回退或全量重新评定；自动和人工调整均只允许维持或提升等级。目标是以有限等级控制参与权限，以有界数据和请求内按需判断实现晋级，不建立荣誉积分、阅读流水或持久化晋级任务。

## 1. Discourse 的设计与本项目取舍

Discourse 的 TrustLevel 是固定的 0～4 枚举：newuser、basic、member、regular、leader；用户保存数字等级，人工锁定可以阻止自动晋级。Promotion 根据 user_stats 中的访问天数、进入主题数、阅读数、阅读时长和点赞等检查普通晋级；TL3 另有每天运行的晋降级任务，TL4 人工授予。等级变化同时影响自动用户组。近年的 Discourse 将许多功能开关迁移为 allowed groups，保留信任等级组作为授权来源。

参考（2026-10-15 查阅，main 分支会变化）：

- https://github.com/discourse/discourse/blob/main/lib/trust_level.rb
- https://github.com/discourse/discourse/blob/main/lib/promotion.rb
- https://github.com/discourse/discourse/blob/main/app/jobs/scheduled/tl3_promotions.rb
- https://github.com/discourse/discourse/blob/main/app/models/user_stat.rb
- https://github.com/discourse/discourse/blob/main/app/models/user_visit.rb
- https://blog.discourse.org/2018/06/understanding-discourse-trust-levels/

GooseForum 借鉴整数等级、有限信任阶段、人工锁定和组授权，不照搬连续编号、阅读计时、每日扫描和滚动降级。本设计的访问条件比 Discourse 简单，不能据此证明内容质量；具有内容维护能力的社区骨干始终人工授予。

## 2. 等级定义

| 固定整数值 | Go 常量名 | 显示名称 | 晋级方式 |
| ---: | --- | --- | --- |
| 0 | trustlevel.Newcomer | 新用户 | 注册默认 |
| 100 | trustlevel.Member | 成员 | 自动 |
| 200 | trustlevel.Regular | 稳定成员 | 自动，默认条件见下文 |
| 1000 | trustlevel.Core | 社区骨干 | 人工 |

整数同时作为持久化身份和高低顺序，不另存字符串 code 或 rank。Go 使用 `type Level int16` 和显式常量赋值，数据库使用 SMALLINT，JSON 接口使用整数。页面显示名称，不显示 L3 或原始数值。未来可插入 300、400 等等级，社区骨干始终为 1000，无需重编号现有用户。

整数不是数组下标，禁止使用 iota 连续编号或 level + 1 推算下一等级；通过有序静态定义查找下一自动目标。写入和接口入参必须命中已定义值，不能仅检查 0～1000 范围。遇到未知存量值时记录错误并拒绝依赖信任等级的授权，不能因为数值较大自动获得权限。预留间隔不是任意用户可配置等级。

第一期定义为 Go 中的静态注册表，前端从站点 payload 获取定义；不新增等级定义表或任意等级编辑器。新增等级需要代码变更、迁移和明确规则，避免任意后台重排导致授权语义变化。名称通过现有国际化提供。

## 3. 默认晋级规则

所有条件为 AND，年龄从 users.created_at 计算，访问数据从功能上线或注册后累计。

| 目标 | 注册年龄 | 有效访问日 | 不同主题访问数 |
| --- | ---: | ---: | ---: |
| 成员 | 24 小时 | 2 天 | 5 个 |
| 稳定成员 | 14 天 | 7 天 | 20 个 |
| 社区骨干 | 不适用 | 不适用 | 仅人工授予 |

稳定成员的初始默认条件为上述值，后台可以调整。两次自动晋级共用累计进度，不在成为成员后重置；不要求发帖或互赞，不因不活跃自动降级。

有效访问：使用已认证的浏览器会话，成功打开一个正常已发布、本人可读且非本人创建的主题。HTML 首屏和 React 导航访问使用同一个后端入口；分页拉取、预取、HEAD、错误响应、草稿、管理预览、后台请求、Agent API 均不计。客户端显式预取请求标记须被识别；没有标记的自动访问无法与人工访问彻底区分，这是低成本方案的边界。

同一个主题的不同楼层算一个主题。同一天访问任意多个主题只算一个访问日。统一使用 UTC 日期作为统计日，界面明确口径，不依赖服务器本地时区；24 小时年龄要求独立于日期，跨午夜不能绕过。只接受大于上次日期的新日期，乱序请求不能令日期倒退或重复累计。

条件准确名称为“访问主题”，不称为“阅读完成”。禁止为此增加停留计时、滚动检测、前端心跳或每次访问流水。

有效账号必须未删除、当前无封禁/暂停，且满足现有 NeedsEmailVerification 政策。受限期间不累计进度、不自动晋级，解除后保留此前进度；邮箱政策复用现有逻辑，不要求所有历史账号重新验证。

## 4. 数据存储

等级与小型进度放在 users 同一行，避免每次用户授权增加关联查询，也能一次原子更新进度和等级。不放 user_statistics：现有活跃统计有内存批处理，不能作为授权事实；不放 kvstore：现有未读访问标记只有 48 小时 TTL。

新增字段：

| 字段 | 类型/默认 | 用途 |
| --- | --- | --- |
| trust_level | SMALLINT, 0 | 当前等级，Go 类型 Level（int16） |
| trust_level_locked | bool, false | 禁止自动晋级，人工锁定阻止自动晋级 |
| trust_visit_days | uint32, 0 | 累计有效访问日 |
| trust_last_visit_day | varchar(10), 空 | 最后计入的 UTC 日期，YYYY-MM-DD |
| trust_topic_ids | text, JSON 数组 [] | 最先访问的不同主题 ID，最多 20 |
| trust_version | uint64, 0 | 乐观并发版本 |

通过 Go JSON serializer 处理 ID 数组，不依赖数据库 JSON 操作；数组以十进制整数保存，仅服务端使用，最多约 421 字节文本。无需单独主题计数字段，len(ids) 即为进度。不建立用户与访问主题的关联表，不对这个数组建索引。常规用户列表不查询数组。

只给 trust_level 建普通索引，用于后台筛选、统计和批量受众判断；其余字段按用户主键访问，无额外索引。SQLite 使用其整数存储规则，不假设 SMALLINT 在所有数据库都固定占两字节。局部读取定义用途明确的小型读模型，通过 Model(&users.EntityComplete{}).Find(&ReadModel) 推导列。

访问日使用整数累计，每个有效访问日最多更新一次，不封顶 7 天；主题集合仍封顶 20 个，主题阈值在此预算内可配置。未达稳定成员、未锁定的用户持续累计访问日、采集主题至 20 个，不因当前配置阈值较低而提前截断；达到稳定成员后停止。提高阈值不会降级已有成员，新阈值只影响尚待晋级的用户。超过主题采集上限的条件第一期拒绝保存；未来扩大预算必须另有迁移说明，不能宣称能恢复未采集的数据。

users 只保存当前等级、锁定状态及晋级所需进度，不增加 trust_level_reason 或 trust_level_changed_at。变更原因、操作人和时间仅保存在等级历史中，后台按需查询，不在常规认证或用户列表中加载。

users 通用资料保存、用户自己提交的 JSON、OAuth 更新不能写这些字段；新增专用 repository 方法更新，列入敏感字段保护测试。

## 5. 触发与调用顺序

新增 app/service/trustlevelservice，集中定义等级、纯规则判断、RecordTopicVisit、Review、SetLevel。数据库查询与条件更新放 users 的专用 *_rep.go，service 不散落 SQL。

### 主题访问

在 app/http/controllers/forum/topic.go 的 TopicDetail 中接入，位置是主题、首帖、访问权限和发布状态检查成功之后、构造最终 payload 之前。调用独立的 RecordTopicVisit，不放进 topicunseenservice.MarkVisited：创建主题和回复也调用 MarkVisited，不能让它们冒充阅读。

流程：读取本请求的配置快照和小型信任进度模型 → 校验账号状态 → 推进新访问日和未达采集上限的主题集合 → 根据当前启用的条件检查所有自动目标 → 一次条件更新写进度和最终等级。达到稳定成员或人工锁定时直接退出；满足多个目标时一次升到最高自动等级。关闭自动晋级只停止晋级判断，未锁定且未达稳定成员的用户仍按原预算累计访问进度。

晋级之后重新构造当前请求的用户展示数据和访问快照，使本次响应显示新等级。当前主题的原始读取授权不能依赖“读完它以后才能获得的等级”。

### 仅时间条件成熟

没有定时任务。认证返回的账号状态在请求内复用，稳定成员和锁定用户不增加晋级查询。普通页面/操作的无进度复核使用最多 4096 项、每用户一分钟的内存缓存；轮询通知、未读、聊天、帖子窗口和图片请求跳过复核。主题详情跳过中间件复核，在有效访问入口立即处理一次进度，不受一分钟节流影响。时间条件成熟后，普通请求最迟在节流到期后复核；不必再找到新的主题。

认证小型账号状态增加 trust_level/locked/created_at，复用已有账号状态读取；进度仅在成功主题访问，或年龄满足后有必要复核时读取。通过 Gin 请求上下文复用本请求结果，不把等级写入长期 JWT 作为权限来源。邮件激活后下一次正常请求复核；写 API 只复核既有进度，不增加访问进度。

### 人工调整

后台专用操作提交 level（整数）、locked、reason、expectedVersion。只有 Admin 可调整等级或锁定，不复用 RoleManager/UserManager 权限以免间接授予分类维护能力。管理员可以直接授予社区骨干；低于当前等级的提交一律拒绝。人工锁定阻止自动晋级，解锁后下次正常请求复核已有进度。首次实现不允许自己调整自己的等级。

普通晋级不修改角色、TokenVersion、OIDC 凭据，不要求重新登录；调整后的新请求读取新等级，已完成授权的在途请求沿用现有项目语义。没有等级回退入口，人工调整也不能降低等级。

## 6. 并发与失败

进度和等级一次 UPDATE，WHERE 包含 id、trust_version、当前 trust_level/locked、未删除，以及读取时的账号限制/激活相关字段；SET 更新进度、等级和 trust_version + 1。这样并发浏览不会覆盖 ID 集合，管理员锁定/调整、账号处罚变化也能使旧更新失败。其他敏感账号更新无需共享 trust_version，但须作为条件检查。

自动操作冲突后重读并重算，最多重试一次；仍冲突则略过本次累计，下一次访问再处理。人工操作冲突返回明确冲突，重新加载后提交，不覆盖他人的调整。用户 ID 数组和日期均由服务端产生，客户端不能提交进度。

不新增事务、队列、恢复任务或“最终补齐”机制。浏览统计失败只记录 warning，不阻断正常阅读；授权事实读取失败则拒绝依赖该等级的权限，不从展示缓存猜测授权。

等级历史采用独立 user_trust_level_history 表，仅记录等级/锁定变化：id、user_id、from_level、to_level、from_locked、to_locked、source(auto/admin/migration)、operator_id、reason、created_at；from_level/to_level 同为 SMALLINT，索引 (user_id,id)。不记录日常进度。人工提交的 reason 仅写历史，不复制到 users；自动变更通过 source 和目标等级说明，不生成重复原因文本。

状态更新成功后同步写历史。自动历史失败告警，接受审计缺口；人工历史失败返回“状态已更新，历史写入失败”，页面刷新事实状态，不误报整体回滚，也不承诺重试补全。历史是解释用途，不参与权限和晋级判断。后台展示最新历史记录的原因和时间，不将其当成当前状态的权威元数据；历史缺失时显示无历史记录，不从 users.updated_at 推测等级变更时间，也不把最近一条历史冒充当前状态。这一取舍遵循本仓库避免为恢复引入事务/任务的原则。

## 7. 与访问组和分类权限衔接

沿用 access_groups / category_group_permissions；增加系统组 trust:100、trust:200、trust:1000，语义分别为“成员及以上”“稳定成员及以上”“社区骨干及以上”。新用户使用已有 registered，无需重复组。system_key 是少量组元数据的字符串，不在每个用户上重复存储等级名称。

系统组元数据入库以便后台授权；用户成员关系由当前有效整数等级和组阈值动态推导，不向 access_group_members 写每个用户的等级成员行。这样等级调整只改一个权威字段，不需要同步派生关系。系统等级组不能申请、邀请、手动加人或删除，不计入 32 个自定义组上限。后台系统组显示动态成员语义，不提供逐用户成员列表或手动维护；管理员通过用户列表的等级筛选查询用户。授权时校验等级必须为已定义值，再比较阈值，不接纳未知等级值。

访问快照 = everyone + registered + 满足等级的系统组 + 自定义组 + 现有管理权限。匿名只含 everyone。继承的是组成员资格，不是自动授予任何分类权限；系统组初建没有分类 grants。某分类同时授权 registered 和 trust:200 时仍取最高 grant，不能用后者撤销前者。要限制新人发帖，应移除 registered 的 create，并授予 trust:100 create。

必须同步改动：

- accesscontrol.Resolve：读取当前信任身份，合并等级组。
- FilterReadableUserIDs：批量读取候选用户的整数等级，校验有效性后按组授权过滤；保持原有公开/注册组快捷返回及管理员/版主例外，禁止逐用户查询。
- 列表缓存 ListCacheAudience：从 registered 改为 registered:trust:<level>；保留自定义组/版主禁用共享缓存逻辑。新增等级后不能共享错误的主题列表。
- 搜索、主题详情、分类选择、附件下载、通知列表及推送/邮件发送前的受众校验：统一使用同一访问语义，排查所有直接查询成员关系的路径。
- 后台分类授权与访问组页面：展示只读系统组身份与“及以上”语义；迁移/编辑后刷新系统元数据、grants 和相关列表缓存。

等级本身不授予后台角色、全局内容管理或版主身份。社区骨干默认也没有其他人私有内容的访问权；给 trust:1000 组的分类 grant 才产生权限。已有显式授权/管理角色仍有效，不借信任等级取消现有管理员能力。

## 8. 功能权限与配额

第一期明确落地的权限是现有分类四档 read/reply/create/manage，不新增一套重复分类 ACL。发布/回复仍先经过账号限制和邮箱检查，再检查分类权限。

社区图片上传使用 pageConfig 新增 TrustSettings 的等级限制，默认沿用当前行为；不在控制器中写 trust_level == 200。读取附件仍按所属内容可读性校验，上传权限不能替代下载 ACL。

若第一期需要实际新人限制，默认建议：当前上传通道只支持图片，非图片附件仍由现有通道拒绝；新用户每篇内容最多 1 张图片、2 个外链和 2 个有效用户提及；成员及以上解除这些等级限制。图片大小、类型和全站上传政策照旧。是否启用这些限制是独立站点设置，迁移默认关闭，避免升级后突然拒绝原有工作流。

新增内容限制必须在 topicwriteservice/postwriteservice 以及最终发布/编辑路径统一校验，不能只在 HTTP 控制器校验；图片、外链和提及复用 Markdown 结构解析结果与实际识别的用户，不能用正文正则计数。草稿可保存，在发布时校验。编辑也校验最终内容，失败返回具体限制。

图片数量按单篇最终发布内容中实际可渲染的图片节点计数，主题首帖和每条回复分别计算，不按整个主题累计。本地上传和远程图片均计入，同一地址出现多次按出现次数计；代码块、行内代码、纯文本 URL 不计。若允许 HTML 图片或其他可生成图片的扩展，须在统一规范化后的渲染结构中一并计数，不能绕过限制。头像、站点图标等正文以外图片不计。

maxImagesPerPost 是发布内容限制，allowImageUpload 是上传权限，两者独立：禁止上传不代表可以绕过正文远程图片数量限制。上传接口不检查单篇图片数，因为上传时尚未确定最终内容；前端可提前提示，后端发布/编辑校验为准。无需新增图片计数表、抓取远程图片或持久化计数。

不把高频配额强行放入等级统计。现有全站发帖限制继续有效；按等级每日点赞配额、编辑期限属于后续独立实现，需要自己的精确计数和并发设计，本期不宣称已覆盖。

TrustSettings 通过 pageConfig 存储和 hotdataserve 缓存，沿用后台配置保存/失效模式；Admin 才能修改配置。系统整数等级定义和采集上限第一期不开放编辑；晋级阈值和等级限制按下面结构配置。

### 8.1 配置存储与完整结构

新增 pageConfig.TrustSettings 常量，对应 page_config.page_type = trustSettings，所有信任配置存为同一行 JSON。默认值由 pageConfig.DefaultTrustSettings 提供（沿用现有 Agent 配置的组织方式），repository 提供专用读取/保存方法，hotdataserve 提供缓存和清理方法。不把这些后台设置放进 config.toml，不给每项配置建表。

默认配置如下：

```json
{
  "schemaVersion": 1,
  "autoPromotionEnabled": true,
  "promotionRules": [
    { "level": 100, "enabled": true, "minAccountAgeHours": 24, "minVisitDays": 2, "minTopicsVisited": 5 },
    { "level": 200, "enabled": true, "minAccountAgeHours": 336, "minVisitDays": 7, "minTopicsVisited": 20 }
  ],
  "restrictionsEnabled": false,
  "levelLimits": [
    { "level": 0, "allowImageUpload": true, "maxDailyTopics": 3, "maxDailyReplies": 10, "maxImagesPerPost": 1, "maxExternalLinksPerPost": 2, "maxMentionsPerPost": 2 },
    { "level": 100, "allowImageUpload": true, "maxDailyTopics": null, "maxDailyReplies": null, "maxImagesPerPost": null, "maxExternalLinksPerPost": null, "maxMentionsPerPost": null },
    { "level": 200, "allowImageUpload": true, "maxDailyTopics": null, "maxDailyReplies": null, "maxImagesPerPost": null, "maxExternalLinksPerPost": null, "maxMentionsPerPost": null },
    { "level": 1000, "allowImageUpload": true, "maxDailyTopics": null, "maxDailyReplies": null, "maxImagesPerPost": null, "maxExternalLinksPerPost": null, "maxMentionsPerPost": null }

}
```

promotionRules 的每条规则中三个条件同时满足才晋级，0 表示不要求该项。levelLimits 按当前精确等级匹配，必须覆盖所有已定义等级，不做隐式逐级合并；这样管理员可直接看出每级的完整限制。整数上限 null 表示本系统不追加限制，0 表示不允许任何对应的图片/外链/提及；Go 使用可空整数，不能把 0 和未配置混为一谈。

autoPromotionEnabled=false：保留当前等级、进度和人工调整能力，停止自动晋级。规则 enabled=false：停止向该目标自动晋级；更高目标仍可独立满足并直接晋级，不要求先取得禁用的中间等级。社区骨干不接受自动规则，不开放按数量自动成为骨干。

restrictionsEnabled=false：不应用 levelLimits，继续使用现有发布和上传政策；等级系统组的分类授权仍然生效。开启后，对所有当前用户的新写入按对应等级限制执行，不追溯修改历史内容。锁定仅影响自动晋级，不豁免权限限制。


### 8.2 配置校验

- 自动规则目标仅限 100/200，每个目标恰好一条；等级限制每个已定义等级恰好一条。拒绝未知值、重复、缺失、未知 JSON 字段和超出类型范围的数值。
- 注册年龄为 0～87600 小时，访问日为 0～36500，主题数为 0～20。固定采集预算显示在后台输入旁；超过预算明确报错，不静默截断。
- 两个目标的条件逐项非递减，即稳定成员不能比成员要求更低；每条启用规则至少一个条件大于 0，避免误配置后全员直接晋级。
- 图片、外链、提及上限为 null 或 0～100；限制配置可按等级独立设置，不假设高等级一定更宽松。异常的收紧在保存预览中提示，合法配置仍可保存。
- 全量校验成功后一次保存 JSON；不先写部分字段。已存在的配置解析失败或版本不支持时返回配置错误，禁止悄悄回退默认值放宽权限。只有完全不存在配置时才使用初始化默认值。

### 8.3 生效、缓存与配置修改

后台提供 get-trust-settings / save-trust-settings，均需 Admin。读取返回完整规范化配置；保存同样提交完整配置，第一期沿用站点设置最后一次成功保存生效的方式，不额外增加配置版本锁。

保存成功后立即清理本进程配置缓存及无进度晋级复核缓存；人工调整也清理该用户复核缓存。其他进程配置最多 5 秒 TTL 更新，无进度晋级复核可能延迟最多一分钟，主题访问仍按当前配置立即检查。保存前已开始的请求可能沿用旧规则。不为配置修改增加广播或任务队列，后台明确此生效边界。

降低晋级条件：符合条件的用户在下次正常请求晋级，不全表扫描。提高条件/关闭规则：已获得的等级保留；尚未获得目标等级的用户按新条件判断。重新启用规则：继续使用已保存的进度。调整等级限制：后续请求按新配置校验，与历史晋级时采用的规则无关。

只修改条件或操作限制不改变分类 grants，无需刷新分类列表缓存；等级身份变化仍按现有设计更新用户展示与缓存受众。分类授权修改继续走现有分类授权和缓存失效流程。

### 8.4 与现有设置的合并及后台界面

最终可执行操作 = 账号安全检查通过 AND 分类能力满足 AND 现有全站政策满足 AND 新信任政策满足。新配置只能追加限制，不能绕过现有文件类型、大小、频率或全站禁用设置；多个数量上限共同适用时取有效上限的最小值。已有管理员/版主分类管理授权照旧，但浏览器社区发布与上传不隐式豁免等级内容限制。

当前服务没有非图片附件上传通道，因此不增加 allowAttachmentUpload 这类无实际效果的配置字段；后续开放附件通道时另行增加权限校验。

后台“信任等级”页分为“晋级条件”“等级限制”两个视图。条件视图逐目标编辑启用开关、注册小时数、访问日和主题数，骨干显示人工授予。限制视图按四个等级列出上传开关、每日新建主题数、每篇图片/外链/提及上限，明确“继承全站限制”的 null 语义。页面同时显示现有分类授权入口，不在此复制一套分类权限编辑器。

后台显示每个等级的完整现值，保存时全量提交并显示成功/失败结果；不计算全站受影响人数，避免每次修改触发全表扫描。第一期没有独立的变更预览对话框。本人进度接口和前端能力展示统一读取同一份配置，不保留硬编码的 24 小时/2 天/5 主题。

第一期配置能力包含上述条件、每日新建主题数、每日新建回复数、上传、正文图片数、外链和提及限制。图片数需验证本地/远程、重复地址、代码内伪图片、HTML/扩展图片、首帖/回复分别计数，以及编辑超限场景。按等级每日点赞数、上传次数和编辑期限不提供空壳设置，仍以已有全站规则为准；增加这些能力时需要补充具体计数和并发方案。

## 9. 接口与界面

共享 viewer、用户卡片和用户资料响应提供 trustLevel 整数；等级名称由前端统一映射（支持现有四种语言）。本人进度接口另提供 definitions、locked。公共界面仅显示名称，不公开访问 ID、锁定原因或管理员备注。

后台采用现有路由命名风格新增 user-trust-level（详情）、set-user-trust-level（修改）、user-trust-level-history（游标分页）。修改返回最新版本和状态。用户列表支持整数 trustLevel 筛选，沿用现有用户分页方法并排除 trust_topic_ids 查询，不返回访问数组；详情页显示进度、人工调整、锁定和历史。

## 10. 上线与未来扩展

迁移版本为 25，在现有 migration/datamigration 流程添加字段和历史表，幂等创建等级系统组；不修改现有分类 grants，不默认开启新的内容限制。

存量账号统一迁移为成员（100），原有受限状态保留、没有凭空增加访问进度，也不逐用户生成迁移历史；新注册账号默认新用户（0）。利用迁移版本记录区分新旧用户，不能在每次启动时重复把新用户升为成员。存量账号升稳定成员（200）需要上线后累计进度；不从浏览总数或 48 小时未读记录推算不存在的历史。既有管理员不会自动成为社区骨干（1000），管理角色原有权限保持有效。

## 11. 资源预算和验证

每用户新增状态为常数空间，主题集合最多 20 个 uint64；两次自动升级完成后不再读取/写入访问进度。重复访问达到上限的主题或已达上限的日期不产生进度 UPDATE，但年龄条件成熟仍可产生一次晋级 UPDATE。

默认进度变更由最多 20 次新主题和每天最多一次跨日事件驱动，另有最多两次年龄成熟晋级写入；同一次事件合并一条 UPDATE。并发冲突和人工操作不计入此预算。用户行为导致的无效读取仍存在，不能称为零开销；第一期不再加全局进度缓存，以减少权限缓存失效复杂度。

必要验证：配置完整性和数值范围、null/0 差异、采集预算边界、全局/单目标自动晋级开关、条件升降后的既有等级保留、精确等级限制、配置缓存失效与损坏配置拒绝放宽、有效整数枚举校验（含未知值、负数、溢出）、插入中间等级不改变社区骨干身份、规则边界、UTC 跨日与乱序、ID 去重/上限、两级直升、锁定和人工调整、受限与邮箱政策、并发 CAS 合并、SQLite/MySQL/PostgreSQL serializer 兼容、资料保存不覆盖敏感字段、HTML/React 同入口且预取不计、列表缓存隔离、批量通知过滤、私有附件/搜索访问、迁移重跑无二次晋级。用查询日志确认达稳定成员后没有进度查询/写入，重复已计访问不写库。

推荐实施顺序：数据与纯规则 → 请求触发与人工管理 → 动态系统组和全部授权读取 → 展示与可选新人限制。每一阶段配对应行为验证；只修改此设计文档无需构建 resource，真正修改前端后按 config.toml 的环境运行 pnpm dev 或 pnpm build。

## 14. 等级每日主题配额补充

主题和回复使用独立额度：maxDailyTopics / maxDailyReplies。新增回复上限默认新用户 10，其他等级 null；旧配置缺失字段按 null 处理。null 不追加等级限制，0 禁止新建回复，正整数最多 100000。回复按服务器日期统计 posts 中 post_no > 1 的记录，排除首帖，删除/审核中的回复仍计入；仅创建时检查，编辑不计次。浏览器与 Agent 共用 postwriteservice 校验，Agent 超限返回 429。沿用主题配额的尽力并发语义，不增加计数表或事务。

直传完成接口在读取待上传对象前重新解析当前社区上传策略，包括等级上传开关；禁止使用修改权限前申请的直传凭据完成发布。管理后台素材上传保持独立管理授权。策略校验失败不消费待上传对象，可在权限恢复后按现有有效期重试。

每级新增可空整数 maxDailyTopics，默认新用户 3，其他等级 null。旧配置缺少此字段时解析为 null，保持既有行为；0 禁止新建主题，null 不追加等级上限，正数上限为 100000。限制开关关闭时仅执行已有全站配额。

在 topicwriteservice 的新建入口统一检查，覆盖浏览器与 Agent API；新建草稿也计入，编辑、已有草稿发布和回复不新增主题记录，不重复扣配额。统计口径沿用 topics 的现有每日创建查询（服务器日期），不同于晋级访问日的 UTC 口径。全站与等级上限取严格值，一次 COUNT 查询完成判断；不增加用户字段、计数表或定时任务。

该配额沿用现有“检查后创建”的并发语义，不是严格原子预留；多个并发请求可能同时通过检查。不为这一反滥用配额增加事务或持久化计数机制。浏览器返回具体等级每日上限消息，Agent 超限返回 429；编辑/回复不受此项限制。
