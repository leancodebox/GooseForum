# GooseForum Markdown 扩展设计

日期：2026-10-03。状态：扩展基础与用户提及已实施；其他扩展保留为预案。

源文版本 `0` 保持旧 Markdown 语义，版本 `1` 启用扩展。新发布内容使用版本 `1`；
历史内容升级时保留原提及基线，避免补发历史通知。未知行内/块级扩展保留原文、
内部语法不激活；Go 与前端共用 `testdata/markdown-extensions/mentions.json` 验证。
目前只注册 mention；poll、details、note、spoiler 尚未提供业务或编辑器控件。

目标是让未来的提及、投票、折叠内容等沿用稳定的语法和接入规则，保证阅读、
源码编辑、可视编辑及导出的语义一致。可靠、好用优先，不要求与 Discourse 语法兼容。
目前只有 @提及属于已实现的 Markdown 功能；投票等用于未来扩展预案。双因素认证、草稿恢复、封禁、
登录日志和注册限制独立设计，不属于本文的 Markdown 扩展机制。

## 1. 当前基础

- 后端使用 Goldmark，入口为 `app/http/controllers/markdown2html/markdown2html.go`。
  已有 `AnalyzePostContent`，可从一次 AST 解析产出 HTML 与图片引用。
- 前端预览使用 `resource/packages/markdown/src/index.ts` 中的 markdown-it。
- 可视编辑使用 `resource/packages/ui/src/lib/visual-markdown-schema.ts` 中的
  ProseMirror schema、MarkdownParser 和 MarkdownSerializer。
- 三个入口目前支持的语法并不完全相同；可视编辑已有不支持内容的检测入口。
- 用户允许改名。当前用户名校验为 ASCII 字母、数字、下划线、连字符，长度 4–32。
  因此只保存 `@username` 无法保证改名后的身份指向。
- 回复模型已有 `RenderedVersion`。它是渲染实现版本，不等于源文语法版本。

沿用现有库，在其原生扩展接口上适配规则；不引入新的 Markdown 引擎。

## 2. 总体决策

1. 标准 Markdown/GFM 保留；现有表格、代码围栏、任务列表等不重写。
2. 自定义扩展按行内、块级两类管理，采用带名称的方括号标签家族。
3. `@username` 是行内输入快捷方式；需要稳定身份时保存为统一的引用标签。
4. 一个功能只设一个规范存储形式。快捷输入可以不同，保存后的语义必须统一。
5. 源文是内容定义，数据库存用户身份、投票记录等业务状态。
6. 解析、渲染、导出不产生通知、不创建投票、不写数据库。

选择标签家族是本项目的设计建议，不代表行业统一标准，也不意味着支持任意 BBCode。
只接受显式注册的扩展，不把用户标签当 HTML 执行。

## 3. 语法家族 V1

### 3.1 行内扩展

```markdown
你好 [mention user="123"]@alice[/mention]，请看这个方案。

[spoiler]这里是剧透内容[/spoiler]
```

通用形态：`[name key="value"]内容[/name]`。
行内内容不能跨段落；每个扩展声明是否允许普通行内 Markdown。
mention 的内容是纯文本标签，不允许嵌套链接、图片或其他扩展。
用户在界面中看到的是 `@alice`，无需手工输入 ID 或标签。

### 3.2 块级扩展

```markdown
[details title="展开说明"]
这里可以写 **Markdown**，也可以写列表。

- 第一项
- 第二项
[/details]

[note kind="warning"]
这里是提示内容。
[/note]
```

通用形态：开始标签单独一行，正文若干行，同名结束标签单独一行。
空内容也用开始和结束标签，不额外引入自闭合、`:::...`、JSON 块等平行语法。
现有 Mermaid 等成熟代码围栏约定继续使用，不改造成标签。

### 3.3 标签与属性

- 名称和属性名使用小写 ASCII，匹配 `[a-z][a-z0-9-]*`，大小写敏感。
- 开始标签仅允许名称及空格分隔的 `key="value"`；属性值统一双引号。
- 属性值中 `\"` 表示引号，`\\` 表示反斜杠，`\]` 表示右方括号。
  不允许换行、控制字符；不做 HTML 实体解码或 JavaScript 表达式求值。
- 属性顺序不影响语义，序列化按扩展定义的固定顺序输出。
- 重复属性、未知属性、非法枚举值不静默忽略。预览保留原文并显示诊断；
  新发布时阻止有错误的已注册扩展，草稿允许保存不完整内容。
- 每个扩展明确哪些属性必填、默认值、长度与数量上限；没有通用任意属性袋。
- 公共 ID 在前端契约中用十进制字符串，避免 Go uint64 转成 JavaScript number 丢精度。
- 写 `\[mention ...]` 可表达字面量开始标签；反斜杠转义遵循 CommonMark 奇偶规则。

### 3.4 上下文、嵌套与冲突

- 代码块、行内代码、链接文本及目标、自动链接、图片替代文本、HTML 片段中不识别扩展。
- 标准 Markdown 链接保持原有含义。例如 `[poll](https://example.com)` 仍是普通链接。
- 块标签必须处于当前 Markdown 容器的块边界，允许相对容器最多三个空格缩进；
  四空格缩进代码、围栏代码中的标签均为字面量。
- details/note 可以包含普通 Markdown；是否包含其他扩展由注册规则决定。
  同名嵌套用栈配对，关闭当前最内层标签，禁止跨层交叉关闭。
- poll 等有业务状态的块不允许放入引用块或其他扩展内部。复制引用不得创建第二份投票。
- 引用块中的 mention 可以显示链接，但不产生提及通知；标题中的 mention 同样只展示。
- V1 建议上限：嵌套 8 层、单标签 1 KiB、单篇 100 个扩展节点；
  超限报告错误，实际限制在实施时结合既有正文上限验证。
- 畸形输入不能产生递归失控或反复全篇扫描。采用有界扫描，失败回退不重新扫描已处理区段。

### 3.5 未知、不完整和禁用扩展

- 未注册标签保留原文，作为不透明内容，不解释其内部属性或业务行为。
- 缺少结束标签、交叉关闭等输入保留原文，不能把后面的正文静默吞入扩展。
- 可视编辑器能表示时使用携带原文的不透明节点；不能可靠表示时保持源码模式，
  明确提示不能切换。不得经“打开、保存”删除标签或改变身份。
- 已注册但禁止创建的扩展仍允许阅读历史内容。暂停投票应停用交互，而不是删除正文。
- 普通格式允许规范化空白；稳定引用 ID、投票 key、未知扩展原文不能被重写。

## 4. @用户提及

### 4.1 输入与规范存储

- 输入 `@` 弹候选；选择用户后插入 `[mention user="123"]@alice[/mention]`。
  可视模式渲染为行内提及节点，源码模式允许看到完整语法。
- 手写 `@username`：服务端发布前在合法文本位置解析，批量查找后转换为规范标签。
  未知用户保持普通文本；同名匹配有歧义时不能任意选一个。
- 匹配规则沿用现有账号查找语义，不借此修改全站用户名大小写或唯一性规则。
  实现前先核对三个数据库后端的既有行为和历史账号。
- 原文转换只发生在明确的保存流程；渲染不能偷偷改源文。
  规范化后的正文必须返回编辑器并更新已保存快照，本地草稿亦以返回值为准。
- 规范化最多增加一次有界解析；常规已规范源文复用一次解析结果。
  不把提及替换为链接后反复重新解析全文。
- 用户改名后引用仍指向 user ID，显示当前用户名；原标签用于用户删除后的降级展示。
- 手工提交 ID 不绕过用户状态和上下文检查；服务器验证真实目标，标签本身不是权限证明。

### 4.2 识别边界

| 输入 | 处理 |
|---|---|
| `你好 @alice`、`**@alice**` | 可以识别自然输入 |
| `mail@alice.com`、URL 内的 `@` | 不识别 |
| `\@alice`、代码中的 `@alice` | 不识别 |
| 链接标签、图片 alt 内的 `@alice` | 不识别 |
| 未知、被删除的用户名 | 保持普通文本 |

用户名 token 必须完整匹配，不截断长名称去匹配短账号；连字符、下划线应作为名称的一部分。
前端候选不是保存语义的权威判断。中文邻接、标点与历史名称须纳入共用用例。

### 4.3 通知规则

- 第一阶段仅主题和回复产生通知；私信、简介、签名、公告不产生提及通知。
- 不通知自己；匿名作者、草稿、待审、删除和拒绝内容不发送。
- 仅对具有内容读取权限、允许接收且未处于账号封禁状态的目标发送。
  通知摘要及链接不能泄露受限板块，读取通知时仍校验当前内容权限。
- 单篇最多 20 个不同收件人，超过上限阻止发布并指出问题，不悄悄截断。
- 编辑只通知尚未通知过的新目标；移除后重新加入、重复保存不重复通知。
- 待审内容在批准时按最终正文发送。去重依据内容身份和用户 ID，
  复用/扩展现有通知唯一约束，不通过持久化投递任务实现。
- 与直接回复通知重复时合并一条，直接回复语义优先。

## 5. 投票设计预案

投票用于验证块级扩展规则；列入设计，不等于本轮实施。
V1 建议只允许主题正文创建，单主题最多 3 个投票，每个 2–10 个选项。

```markdown
[poll key="theme-choice" mode="single" results="after-vote"]
你喜欢哪种主题？

[option key="light"]浅色[/option]
[option key="dark"]深色[/option]
[/poll]
```

- `option` 是 poll 内部专用子元素，必须独占一行，文本不跨行，
  不支持 HTML、提及和嵌套扩展。不是一个可在正文任何位置使用的公共功能。
- 所有属性仍遵循同一语法规则。编辑器提供投票表单，不要求用户手写标签。
- key 是该内容内的稳定局部标识，数据库唯一身份为“内容 ID + poll key”。
  选项 key 稳定，不能用位置或显示文本作为投票对象。
- V1 支持 single/multiple；多选提交非空集合且不超过选项数，不增加选择上下限配置。
- 结果展示支持 always/after-vote/closed，默认 after-vote；截止时间暂由业务界面设置，
  后续若放入正文，必须增加明确的带时区时间属性规范。
- 正文存定义；数据库存投票、选项、投票记录及状态。用户的投票、计数不写回 Markdown。
- 发布服务显式同步定义，预览只显示模拟选项，不创建数据。
- 有人投票后冻结选项身份、文本、模式及问题；仍可关闭投票或修改主题其他内容。
  V1 不提供破坏性“清空结果后修改”。删除投票须明确确认，恢复同 key 保留原结果。
- 未投票前允许修改；复制到新主题创建独立投票，同一主题重复 key 阻止发布。
- 单用户记录以“poll ID + user ID”唯一。更换选项更新同一记录，
  并发投票、关闭与编辑采用必要的事务/并发控制保证业务一致性。
- 每次投票在服务端校验当前内容可见性、账号写权限、截止与关闭状态。
  初始页面批量装配投票状态；不为每个投票单独请求，不持续轮询结果。
- no-js/导出至少显示问题、选项和原站链接；未登录可读，投票需要登录。

## 6. 为其他扩展保留的位置

| 扩展 | 分类 | 设计约束 |
|---|---|---|
| spoiler | 行内展示 | 可隐藏文本，支持键盘操作；不是权限隔离，不能承载秘密 |
| details | 块级展示 | title 为纯文本，正文可用普通 Markdown，导出完整内容 |
| note | 块级展示 | kind 使用固定枚举，按语义显示图标与颜色 |
| 用户/话题/附件引用 | 行内或块级引用 | 稳定 ID，服务端权限过滤，缺失对象有文字降级 |
| 视频/外部嵌入 | 块级展示 | 受控来源，不开放任意 iframe、HTML 或脚本属性 |
| 链接预览 | 普通链接的展示增强 | 不新增语法；单独设计外部请求、缓存和访问边界 |
| 数学公式 | 行内/块级独立词法规则 | 选用成熟约定，先决定 `$` 冲突，公式内不解析提及 |
| 表情 | 行内快捷语法 | 保留成熟 `:name:` 习惯；未知名称作为文字 |

这里只预留规则和能力分类，不提前注册未实现的标签。新增自然输入写法须有明确使用习惯；
其他自定义功能优先沿用统一标签，避免增设多种分隔符。

## 7. 接入架构

### 7.1 共同契约

每个扩展需要声明 name、inline/block、属性 schema、允许的内容与上下文、
解析优先级、文本降级、功能开关及可视编辑支持。源码偏移在 Go 为字节、
浏览器为 UTF-16，跨端契约必须明确转换，不能直接混用。

Go 与 TypeScript 使用各自原生接口，不强求统一 AST。共用语法文档和 JSON fixtures，
比较扩展名称、属性、语义及降级，不强求 HTML 字符串的属性顺序完全相同。
基础标签解析器共享，功能处理器分别注册；不复制一套括号/属性解析器给每种功能。

### 7.2 数据流

```text
源码/可视编辑输入
  -> 纯语法解析（无查库）
  -> 保存服务批量解析身份、校验引用与权限
  -> 必要的源码规范化 + 最终内容分析
  -> 保存正文及确需一致的业务定义
  -> 既有发布/审核流程产生通知

阅读：先验证内容可见性 -> 读取正文 -> 批量装配动态引用/投票 -> 展示
```

可公开缓存的 HTML 不携带“当前用户已投票”等个性化数据；渲染器生成受控占位信息，
业务状态按当前权限装配。预览中的未知身份不伪装成已经验证的账号。
所有输出文本/属性转义，引用 URL 由应用生成；不接受用户提交事件属性或任意 HTML。

### 7.3 代码归属建议

- 后端纯语法扩展放在独立 bundles 包；逐步由现有 markdown2html 入口调用，
  只做完成扩展所需的边界调整，不顺带重构所有 Markdown 调用。
- 前端预览和可视编辑共用 `packages/markdown` 的词法插件/扩展定义；
  ProseMirror schema 和 serializer 在 UI 包适配，不让底层解析包依赖论坛运行时。
- 用户批量解析、通知、投票归各自 service；展示组件由主题层承接。
- UI 包与 Markdown 包的依赖方向保持单向。契约在 client/contracts 装配。
- 注册为静态代码清单，无动态插件安装、运行用户代码或通用数据库钩子。

## 8. 旧内容与版本

- 设计增加明确的源文格式版本：legacy 为 0，扩展格式 V1 为 1，
  与已有 RenderedVersion 分开；主题和回复都需要覆盖。
- 旧正文按 legacy 读取，不因升级把历史字面量标签或 `@用户` 自动变成业务功能。
- 新建正文和编辑器统一使用 V1，不提供提及启用开关；旧文提交编辑时升级，可预览差异，
  不通过全库源文重写迁移，不对历史提及补发通知。
- V1 引入新的标签名称属于兼容扩展，不随意改变已有名称含义。
  破坏性改动需新版本和显式迁移设计。
- 渲染版本升级可重新生成 HTML，但不能改变源文版本、创建投票或补通知。
- 禁止在可视编辑器不支持时强制转换后保存；原文保留优先。

## 9. 验收和实施顺序

1. 先确认语法家族、mention 规范存储和旧内容升级行为。
2. 写语法 fixtures，覆盖转义、代码、链接、嵌套、畸形和超限输入。
3. 实现基础标签解析与 opaque 保留，在三条链路验证读取/编辑/保存。
4. 实现 mention 的身份解析、候选和通知。
5. 以 details 验证容器内容，以 poll 验证块级业务状态；分别验收后再扩展。

必须验证：源文 -> 可视节点 -> 源文不丢 ID/key；未知内容原样保留；
中文和 emoji 偏移正确；用户改名、删除、权限变更；审批、匿名和通知去重；
历史源文不被解释成新功能；投票并发、关闭及定义修改；no-js 和移动端降级。
同时检查查询次数、最坏输入解析开销和页面内引用批量加载，不只验证正常截图。
